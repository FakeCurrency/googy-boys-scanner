# Vivek 5.0 — Top 100 things to work on

Built 2026-07-28 from a four-way read-only audit of the live tree at `9c5cd49f`
(engine + scan pipeline · bot/risk/broker · frontend JS · workflows/CI/scripts).
Every item cites `file:line` for code that was actually read, not remembered.

**Ranking rule.** Not by severity alone — by *what has to be true before the next
fix can be trusted*. An alarm that cannot reach you sits above a wrong number,
because a wrong number with a working alarm gets caught and a right number with
a dead alarm teaches you to trust the silence. Within a tier: impact, then blast
radius, then effort.

**OWNER-DECISION** marks anything that changes *which trades get taken*. Those
are yours, not mine — they are collected in Tier 6 and I will not touch them.
Everything in Tiers 0–5 is a defect: the code does not do what its own
docstring, comment, config constant or test name says it does.

- [x] **63. `risk <= 0` is the only plan guard and it does not catch NaN.** `vivek.py:253`

  **SHIPPED (Tier 4d) — and it is a TRADE-AFFECTING change, flagged as such.**
  `not (risk > 0)`. NaN is the only value in Python for which the two tests disagree
  and it is exactly the value that got in: `atr = max(atr, entry * 0.001)` keeps a NaN
  (`0.1 > nan` is False, so `max` returns its first argument) and `swing_low` is a
  rolling min that is NaN over an all-missing window. What made it worth doing ahead of
  louder items is what the NaN does AFTER the plan is built: every gate that should stop
  it is a `>` or a `<`, and all of them are False against NaN, so it passes the lot —
  `gate_grade`'s R:R floor, the bot's `wide_stop` and `stop_too_tight`, and
  `size_position`'s `stop_dist <= 0`. The position is then booked with
  `risk_usd = units * NaN`, and a NaN inside a sum makes every later comparison False,
  which **disarms the daily and weekly loss guards for the whole book** off one bad ATR
  bar. A corrupt row does not merely mis-price itself; it switches off the thing that
  limits the damage. The change is **monotonically REMOVING** — the docstring has always
  promised no plan unless risk is positive, so this enforces the stated contract rather
  than tightening it, and no plan that existed before stops existing. `run.py:177` hands
  `vivek_run.run_market` the IN-MEMORY rows, so `output.py`'s `_finite` NaN-nulling never
  protected this path; that is why it was a live hazard rather than a display one. The
  same form was applied depth-only in `_structural_targets`, documented as unreachable
  today (its sole production caller now refuses first) — worth having because its
  fallback is *worse* than the bug: `[]` means "no structure, use R-multiples", and
  R-multiples off a NaN risk are NaN TARGETS rather than no plan.

daily now") and fixed the same day. Recorded here because the diagnosis is the
useful part and it does not belong to any tier.

- **It was the screenshot-diff gate in `test.yml`, and the smoking gun was the
  fix history**: nine baseline cache-key bumps, v1 → v10, each of which bought
  about a day. That is not ten intentional visual changes, it is one defect being
  reset ten times.
- **Measured rather than reasoned about.** A throwaway probe pinned `/data/` to
  the fixtures — removing the scan data as a variable — and swept only the
  CLOCK: `journal-desktop` steps to **2.39% drift the moment its cached baseline
  is two days old**, against a 2% budget, and sits at exactly 2.39% at 2, 3, 5
  and 7 days. Flat, not rising: journal.js renders relative ages, so this is one
  day-bucket boundary repainting a block of rows, not slow decay.
  `journal-390` is one row behind it at 1.90%.
- **`actions/cache@v4` is what made it permanent rather than transient.** An
  exact key with no `restore-keys` persists and is refreshed on access, so once
  a baseline is two days old EVERY later run fails until the key moves — which
  is precisely what each bump was doing.
- **Why one email a day and not twenty:** test.yml's path filter deliberately
  excludes `public/data/**`, so the ~20 daily scan commits never trigger it. It
  runs on my own pushes, and there are one or two of those a day.
- **The fix is three layers, and only the middle one persists.** The page clock
  is frozen to the fixtures' own `updated_at` so the baseline's AGE stops being
  an input; the cache key gained a digest of the fixtures so a refresh (which
  moves the clock) cuts a FRESH entry that self-baselines and saves; and a
  `.clock` sentinel inside `__baseline__` discards — never fails — a baseline
  drawn by a clock that no longer exists, which is the one case a key bump
  cannot see (a pre-freeze v10 baseline restored from an old cache).
- **The sentinel's limitation is documented in both files rather than hidden:**
  cache@v4 does not re-save on a key HIT, so a discard cannot persist. If the
  fixtures ever move without the key moving, every run discards, re-cuts and
  passes — green, comparing nothing. The reset log names that symptom and the
  remedy in those words, and a test asserts the reset count reaches the summary
  line so the loop is visible.
- **A discard is deliberately not a failure**, and that asymmetry is the whole
  item: a re-baseline costs one run of comparison, a red costs a person's
  attention on a push they cannot act on, and a channel that cries wolf gets
  muted. Muting is the real damage, because the next red is a genuine one.
- Tests: `test/screenshot_sentinel.test.js` (14, slices the sentinel out of the
  shipped e2e file and runs it against real temp directories) +
  `tests/test_screenshot_determinism.py` (13). Five new structural tests,
  mutation-verified. One of them closes a gap that had been open since Tier 5:
  **every `test/*.test.js` must have a step in test.yml or it never runs in CI**,
  a rule that was written down and enforced by nothing until now.

## Out of band — the failure email that OUTLIVED the screenshot fix (2026-07-28)

**Not a TOP100 item, and it is a correction to the section above as much as a
new finding.** The screenshot fix shipped as `9d6221fe`. Viv's next message was
a screenshot of two more failure emails, one of them for `9d6221fe` itself:
*"again and again man..."*

### What I got wrong, stated plainly

The section above diagnosed the screenshot gate from the **fix history** — nine
cache-key bumps, v1 → v10 — and never reproduced a failing run. The inference
was sound and the defect was real, but "this gate has a permanent bug" and
"this gate is what went red on Tuesday" are different claims and only the first
one was supported. The second was assumed, and it was false.

**The screenshot defect is real and is still worth having fixed** — verified in
a real browser this session, not argued: the unfrozen page sees a clock **2.76
days past `FROZEN_MS`**, the fixture book's newest position opened
2026-07-23T17:46Z, and `NEW_POS_WINDOW_MS` is 7 days, so both journal shots were
due to collapse to "No new positions in the last 7 days." on **2026-07-30**. A
dated fuse with two days left on it. It just was not the thing burning.

### The actual cause, found by reproducing the job

`git worktree add -f /tmp/ci-repro 9d6221fe` and run the three jobs locally.
`javascript` green (15 suites + `node --check`), `python` green, `e2e` **red on
the third of five steps**, one line:

```
FAIL  transfer 5.00MB < 5.0MB (deterministic ~3.50)
```

The Lighthouse budget. Composition of that 5.00MB, measured with a response
listener across 35 requests:

| | MB |
|---|---|
| `asx_vivek.json` | 2.06 |
| `phasemap/asx/latest.json` | 1.38 |
| `vivek_backtest_longonly.json` | 0.62 |
| `market_caps` + `asx_prices` + `bot_book` + `regime` + `sector_map` | 0.30 |
| **committed scan data** | **4.15** |
| all code, CSS and fonts together | 0.85 |

**The growth is legitimate market breadth, not bloat**, and that was checked
rather than assumed: live vs fixture `asx_vivek.json` is the same schema with
**343 rows against 204**, every field group scaling with the row count (plans
497.4 vs 282.8 KB, detail 147.8 vs 87.3, analysis 127.3 vs 75.0, spark 109.4 vs
62.3 — 1.68× the rows, 1.74× the bytes). Nothing regressed. **The budget was
gated on how many ASX stocks happened to set up that day.**

### It is the SAME SHAPE as the screenshot bug, which is why one fix did not cover both

Both gates were measuring something that moves on its own, and both therefore
failed on a commit that did not change it. The screenshot gate's moving part was
the **calendar**; the Lighthouse gate's is the **tape**. And the delivery
mechanism is identical: `test.yml`'s path filter deliberately excludes
`public/data/**`, so the ~20 daily scan commits never trigger the gate — the
payload grows silently for days and then the next unrelated **code** push wears
the red. That exclusion is still right (it exists so 20 daily commits don't each
pay a Playwright install), but it means any gate reading `public/data/` is a
delayed-action fuse pointed at whoever pushes next.

**Corollary worth stating on its own: `screenshot-diff` never ran at
`9d6221fe`.** A failing step aborts the job, and lighthouse runs two steps
before it. The screenshot fix was not merely unproven in CI — it was
unexecuted. It has now been run locally, four images, 0.00% drift.

### The fix is two layers, and only one of them is a gate

1. **The gate's server root is STAGED, not `public/`.** A temp dir of symlinks
   to every `public/` entry except `data`, plus one symlink pointing `data` at
   `test/e2e/fixtures/data` — the same fixture set `screenshot-diff` routes to,
   so the two e2e gates now photograph and measure the *same page*. It had to be
   done at the HTTP root rather than with request interception because
   **Lighthouse drives Chrome through `chrome-launcher`, not Playwright**, so
   `ctx.route()` is simply not available to it.
2. **The real payload is still measured, and is structurally incapable of
   failing the run.** Derived from Lighthouse's own `network-requests` audit —
   not a hard-coded URL list, so it stays complete as pages add fetches, and it
   records 404s so a missing fixture is named rather than silently skipped. It
   prints every run and raises a `::warning::` past 7MB. Slimming a 4.45MB
   dashboard payload is a **product decision, not a CI fix**, which is exactly
   why this half reports instead of gating.

With `/data/` pinned the budget could also come DOWN: 5.0MB → **2.5MB**, against
a now-deterministic 1.86MB baseline. Measured after the fix: `transfer 1.86MB`,
`CLS 0.123`, and `live payload ~5.08MB` — which independently corroborates the
5.00MB measured directly off live data by a different mechanism.

### Tests, and the one that was deliberately NOT written

`tests/test_lighthouse_budget.py` (14). **Mutation-verified: 19 mutations, one
at a time, every one caught, all three touched files restored byte-identical.**

- The pass found a **real gap**. `test_the_page_is_loaded_in_measurement_mode`
  asserted `"?lite=1" in src` — and the file's own header comment discusses
  `?lite=1` at length, so stripping the query string off `URL_UNDER_TEST` left
  the gate measuring un-pinned deferred work while the test stayed green **on
  prose**. It now asserts against the URL constant and against
  `lighthouse(URL_UNDER_TEST,` being the navigation call. This is TOP100 #34's
  mirror-drift in its cheapest possible form, and it would not have been found
  by reading.
- **The test I nearly wrote and rejected:** asserting
  `TRANSFER_BUDGET_MB * MB < (size of the real public/data)`. It reads
  `public/data/`, so it goes red on a *quiet* tape — rebuilding the exact
  tape-dependency the fix removes, one level up, in the suite that exists to
  prevent it. The module docstring records this so it does not get "added for
  completeness" later.
