# Vivek 5.0 — Full System State & New-Lens Playbook

**Written:** 2026-09-22 · **Repo:** `FakeCurrency/googy-boys-scanner` · **Branch of record:** `main`
**Purpose:** (1) a complete, accurate picture of where this system is today, for handing to another
engineer or AI; (2) a concrete, fenced procedure for adding a **new, additional scanner ("lens")**
without breaking anything that currently works.

> **How to read this.** Parts 1–16 are the state of the system. **Part 17 is the playbook** — if you
> are here to build the new scanner, read Parts 2, 8, 11, 13, 14, 15 and then 17. Part 15 ("what was
> removed") matters more than it looks: four subsystems have been deleted from this repo, and
> re-introducing any of them by accident is the single most likely way to waste a week.

## Part 0 — TL;DR in ten lines

1. It is a **three-lens stock/crypto scanner** plus a **paper-trading bot** whose book is the only
   track record. Python engines run in GitHub Actions; a static site on Cloudflare Pages reads the
   committed JSON they publish.
2. Markets: **ASX** (~2,000 names), **NASDAQ** (~1,430), **crypto** (top 200 by market cap).
3. The three lenses are **VIVEK** (price reacting at its 200-SMA), **PhaseMap** (liquidity sweep →
   displacement), **Specs** (sub-$0.50 volume-spike breakouts).
4. **HIGH CONVICTION** is a four-cell rule measured off an 8,239-trade replay: grade A/A+ with an
   armed plan in 1W reclaim, 1W break, 3D reclaim or 1D break. Combined edge **+0.212R, PF 1.47**.
5. The **paper bot trades exactly those four cells**, long only, max 30 positions, $5,000 each.
6. There is **no live broker execution**. Paper only. Broker clients survive only as the kill
   switch's flatten path.
7. Everything is scheduled by **GitHub Actions cron with in-job timezone gates** — crons fire a
   deliberate superset and the job decides whether the market is actually open.
8. **Tests gate every push**: ~72 pytest files + 22 JavaScript suites + a Playwright e2e job with a
   screenshot-diff and a Lighthouse budget. A new JS suite that isn't registered in `test.yml`
   **fails the push**.
9. **One Discord channel is live**: a daily high-conviction digest (`morning_plays`). The old alert
   router was removed.
10. Four subsystems were deleted (TURTLE lens, AI BOT page, HORIZON/REGIME panels, MY JOURNAL manual
    side). **Do not resurrect them.**

## Part 1 — What this system is, and who it is for

**Owner:** Vivek, Melbourne, Australia. He trades real money on a real brokerage account. This
scanner is a **decision-support and evidence system**, not an execution platform. As of 2026-09-21
he explicitly stopped using the site to journal his own trades — the manual journal was removed at
his instruction — so the site's job is now narrow and clear:

- **Find setups** across three independent lenses and grade them.
- **Say which are high conviction**, using a rule backed by a walk-forward backtest rather than
  intuition.
- **Run a paper book** by those rules so there is an honest, mechanical track record.
- **Push a short daily list to Discord** so he can chart the names on his phone and share them.

Brand name is **Vivek 5.0** everywhere in the UI. Never "Googy Boys Scanner" (that is only the
GitHub repo name).

### Design philosophy that pervades the codebase

Three principles explain most of the odd-looking code, and you should adopt them:

1. **An alarm that cannot be believed is worse than no alarm.** Repeatedly, a monitor here was made
   *louder* and that made things worse (a failure email every 5 minutes about a fact only the owner
   could change → the channel gets muted → the next real failure is invisible). Several gates
   deliberately stay green-with-a-warning rather than red.
2. **A wrong number that looks plausible is the most expensive bug.** Much of the test suite exists
   to pin *why* a number is what it is, not just its value. Comments carry the reasoning, and tests
   sometimes pin the comments, because the comment is what stops the next reader re-introducing the
   bug.
3. **Display honesty is separate from trade decisions.** Anything that changes *which trades get
   taken* is the owner's call and is fenced off from anything that merely changes *what is shown*.
   Crossing that line without asking is the cardinal sin in this repo.

## Part 3 — The three lenses in detail

All three are **deterministic**. There is no LLM anywhere in any scan path. Given the same bars, they
produce the same output. This is deliberate and must stay true.

### 3.1 VIVEK — the core lens (`scanner/vivek.py` + `scan.py`)

**Thesis:** price *reacting* at its 200-period simple moving average is a high-quality decision
point. Not "price is above/below the SMA" — *reacting at* it.

- **Timeframes:** Weekly (1W), 3-Day (3D), Daily (1D, used as an H4 proxy). Each timeframe gets its
  own independent plan.
- **Grades:** `A+`, `A`, `B+`, `WATCH`. Produced by `score_and_grade()` then `gate_grade()`.
- **Entry types (triggers):** `reclaim` (price crossing back above the level), `retest` (coming back
  to it from above), `break` (breaking down/through). Each plan has exactly one trigger.
- **Armed vs watching:** a plan is `armed` when its trigger condition is actually live now.
- **Per-timeframe plans** carry `entry`, `stop`, `tp1/tp2/tp3`, and metadata.
- **`level_tf`** records which timeframe's SMA the *headline* level belongs to (`weekly`, `3d`,
  `daily`). This is a separate axis from which timeframe the *plan* is on, and the bot gates on it.

Two subtleties that have caused real bugs:

- **`sma_proxy`** — a name with only 60 weekly bars gets a 60-bar proxy, and the row still said
  "200-SMA". The engine now publishes `sma_proxy: bool` beside `sma_window` so a "200-SMA reaction"
  measured on 60 bars is identifiable. It is *instrumentation, not a filter* — nothing is skipped
  for it. Whether to refuse a proxied A+ is an open owner decision.
- **Grade hysteresis** — grades are smoothed across scans so an A+/A boundary wobble doesn't flap.
  `VIVEK_GRADE_HYSTERESIS_MAX_RUNS` bounds how long a grade may be *held without being re-earned*.
  There is a long test (`test_oscillation_never_demotes_AND_THAT_IS_THE_POINT`) explaining why an
  oscillating score correctly never demotes. **Do not "fix" that.** Note: the bot buys
  `grade_raw` (unsmoothed), while the UI shows the smoothed `grade`.

### 3.2 PhaseMap — the trap lens (`phasemap/`)

**Thesis:** a liquidity sweep followed by displacement marks where trapped participants must
transact.

- **Zones are ALWAYS bands, never single prices.** This is a hard rule.
- States: `SWEPT` → `DISPLACED` → `RUNNING` (plus inactive states). The confluence machinery treats
  `{SWEPT, DISPLACED, RUNNING}` as "active".
- Direction: `bullish` / `bearish`.
- Has `tier` grading.
- **The owner's master spec document is the single source of truth.** Detection mathematics and zone
  definitions must **never** be changed without asking him directly. Any parameter change requires
  bumping `RULESET_VERSION` in `phasemap/config.py`.
- Published `latest.json` is **SLIM** — narrations live in a `narrations.json` sidecar. The dated
  snapshot keeps the full schema.

### 3.3 Specs — the discovery lens (`scanner/spec.py` via `spec_run.py`)

**Thesis:** sub-$0.50 names breaking out of a base on a ≥3× volume spike are worth a look.

- Runs on ASX + NASDAQ only (not crypto).
- **Its own backtest says it is a shortlist generator, NOT an entry system.** That caveat must
  survive any UI work. Do not present Specs output as tradeable signals.

### 3.4 Multi-lens confluence

When the same ticker has **direction-aligned active setups on 2+ lenses**, that agreement is
surfaced:

- `scanner/confluence_alert.py` computes alignments and appends to a permanent log at
  `public/data/phasemap/alert_history.json` (rolling 800-cap, ~14 days).
- The deck shows a **WHAT NEEDS MY EYES** strip (`renderEyes()` in `app.js`) ranking alignments —
  triple-lens beats dual, A+ first within a tier.
- The alignment state is **signed**: `+count` means "delivered at this count", `-count` means "seen
  but never delivered". This matters because push delivery was removed — undelivered alignments hold
  negative counts so a future channel's first run pings everything still current without having
  burned anything.
- **The daily edge pipeline ingests `alert_history.json`** and must keep being written.

## Part 4 — HIGH CONVICTION: the four-cell rule

This is the most important business rule in the system and the newest (2026-09-20/21).

### The evidence

A long-only walk-forward replay over 600 names per market produced **8,239 trades**. Broken down by
(timeframe × entry type) — "cells" — four cells carried a real edge:

| Cell | Mean R | n |
|---|---|---|
| **1W reclaim** | **+0.299R** | 691 |
| **1W break** | +0.161R | 122 |
| **3D reclaim** | +0.196R | 1,309 |
| **1D break** | +0.091R | 281 |
| **Combined** | **+0.212R, PF 1.47** | **2,403** |

### The rule

> **HIGH CONVICTION = displayed grade is A or A+, AND at least one of those four cells is ARMED.**

- A name can fire on **up to three** cells simultaneously and wears **one 🎯 per cell**. (1W reclaim
  and 1W break can never both fire — a 1W plan has exactly one trigger.)
- The previous rule was "a 1W reclaim that is A/A+ **or** has ≥2 structural targets". That was *one*
  of the four cells, plus a structural-targets branch that measured **−0.067R** and was dropped on
  the owner's instruction ("Drop it").

### Where it is defined — and the parity discipline

**`scanner/conviction.py` is the single Python definition:**

```python
HC_CELLS = {"1W": ("reclaim", "break"), "3D": ("reclaim",), "1D": ("break",)}
HC_GRADES = ("A+", "A")
MAX_MARKS = 3
```
plus `conviction_cells()`, `conviction_count()`, `is_high_conviction()`, `trade_cell()`.

Importers: `scripts/morning_plays.py`, `scripts/edge_rosters.py`, `scanner/vivek_backtest.py`.

**The browser carries the same table as a JSON literal** in `public/js/app.js` (`convictionCells`,
`hiconvBadge`) and `public/js/chart.js`. `tests/test_conviction.py` **parses those literals out of
the shipped JS files** and asserts they equal `HC_CELLS`. So the badge, chart chip, Discord digest,
roster baseline and backtest cohort cannot silently drift apart.

**The bot deliberately does NOT import `conviction.py`.** It keeps its own copy of the table in
`config.py` so that a display-side edit can never silently change what gets traded.
`tests/test_bot_alignment.py` pins the two tables equal; `tests/test_conviction.py` pins that
nothing under `scanner/broker/` imports the module. **This fence is a pattern you should copy for
any new lens.**

## Part 5 — The paper bot: the only track record

`scanner/broker/vivek_bot.py` (decision engine) + `vivek_run.py` (book writer).

### Live state (2026-09-21)

**14 open positions, 104 closed.** Book at `journal/vivek_bot_book.<market>.json` (canonical,
per-market) with `journal/vivek_bot_book.json` + a public twin as a **derived combined view**.

- Per-market canonical files mean a market's run can only write its own file — cross-market clobber
  is impossible by construction.
- Regenerate the combined view: `python -m scanner.broker.vivek_run --rebuild-combined`
- Audit: `--verify` (the scan and close workflows run this as a **failing gate**).

### Entry rules (as of 2026-09-21, owner-confirmed)

| Rule | Value |
|---|---|
| Grades | `VIVEK_BOT_GRADES = ("A+", "A")` |
| Entry cells | `VIVEK_BOT_ENTRY_CELLS = {"1W": ("reclaim","break"), "3D": ("reclaim",), "1D": ("break",)}` |
| Direction | **LONG ONLY** — shorts explicitly declined |
| Level gate | `VIVEK_BOT_LEVEL_TF_ALLOW = ("weekly", "3d")` |
| Min R:R | `VIVEK_BOT_MIN_RR = 1.5` (to TP2) |
| Max stop | `VIVEK_BOT_MAX_STOP_PCT = 25.0` |
| Max open | `VIVEK_BOT_MAX_OPEN_TOTAL = 30` across **all** markets |
| Per symbol | 1 |
| Per sector | **3, per market** (not global — see Part 16) |
| Cycle tag | `VIVEK_BOT_CYCLE_TAG = "hc4-1"` |

The cells are walked **1W → 3D → 1D**, taking the first armed, complete plan whose trigger sits in
its cell. The **level gate is separate and still applies**: a 1D-break plan is only taken on a row
that is reacting at a *weekly or 3D* level. This is the pre-registered "w3" cohort, replicated
across three disjoint samples (IS / OOS / C3).

**Shorts were presented with numbers and declined.** Every short cell was negative on every market;
the four cells short-side measured **n=793, −0.360R, PF 0.43**. Owner: *"Yeah lets not do shorts."*

**Measured improvement from the rule change:** previous bot rule `+0.094R, n=2718, PF 1.18` → four
cells at A/A+ `+0.212R, n=2403, PF 1.47`.

### Sizing — FIXED NOTIONAL

```
VIVEK_BOT_POSITION_NOTIONAL      = $5,000    per position
VIVEK_BOT_MAX_PORTFOLIO_NOTIONAL = $150,000  total open notional ceiling
VIVEK_BOT_ACCOUNT_EQUITY         = $150,000  (scales the loss guards, not position size)
```

- **Dollars risked therefore vary with stop distance** (~$50–$1,250, typically $250–$500).
  **Position count is the risk dial, not position size.** Do not "fix" this by re-clamping
  `risk_pct` in fixed mode — `tests/test_fixed_notional.py` pins it.
- Setting `VIVEK_BOT_POSITION_NOTIONAL = 0` restores the old 0.35%-risk-per-trade path exactly.
- **Read R, not dollars, across 2026-07-28.** A one-off resize restated every open position's size
  at the new notional. Dollar P&L is not a like-for-like series across that date; R is, because R
  divides by the position's own initial risk. Live proof from the resize: total open P&L moved
  **+$50.84 → −$715.16 while total open R did not move off +1.452R**, with no price change.
- `sizing_mode` is stamped on every row (`fixed_notional` / `risk_pct`) as an audit field.

### Exits

- TP ladder with partial scaling (`tp1/tp2/tp3`, the full ladder sums to **0.90** by design — every
  trade keeps a 10% runner).
- Stops trail; `risk_stop` preserves the **plan** stop so banked R is never rescaled by protecting a
  position.
- A 28-day time stop.
- Manual close via `close_position.yml` with `journal_type=bot`, or the journal page's close-all
  button (which posts a batch to `/api/close`).

### RULES vs OWNER — a reporting subtlety worth knowing

The book has closes from **two deciders**: the mechanical rules, and the owner closing by hand. At
one measurement the rules had `5W-14L, −6.97R` while the owner had `11W-15L, +0.09R`. Pooled, that
reads `16W-29L −6.88R` and blames the ruleset for a book that was half hand-driven. So the deck and
journal **print the split**, never a blended record. An **absent `exit_reason` is treated as a human
act** in all readers. `MECHANICAL_EXITS` is duplicated in three JS files and held together by a
parity test plus a numeric cross-check.

## Part 6 — Risk guards and the kill switch

### `vivek_guard.py` — daily and weekly loss guards

Guards measure a **window**, computed from `day_marks` — the mark each position carried *into* each
session — not from entry. This telescopes exactly: summing every day's window over a position's life
returns its total P&L.

- **`_stamp_day_ref` must be called BEFORE `_mark_sanity`.** The reference has to be the *previous*
  run's `last_mark` so an overnight gap is charged to the session it gapped into. Stamp it after and
  the gap escapes the daily guard entirely.
- **It fails CLOSED.** An unpriced position is re-valued at its own **stop** (the floor on what it
  can still cost), and if that breaches, the guard halts new entries and reports `unmeasured`
  rather than saying all-clear about a book it cannot see.
- The guard **halts new entries for the session; it does not liquidate.**

### `kill_switch.py` + `kill_switch.yml`

Runs **half-hourly, 24/7**. Checks the bot book per market, re-pricing open positions with live
quotes (falling back to last-scan marks). Also hosts the freshness **watchdog**.

`VIVEK_KILL_SWITCH_BROKERS` maps market → brokers that actually hold it
(`asx: ()`, `nasdaq: ("alpaca",)`, `crypto: ("bybit",)`). A book breach is per-market but a broker
flatten is account-wide, so an ASX paper breach must not liquidate a live crypto book. A market
missing from the dict falls back to the legacy try-both flatten **and logs a warning** —
deliberately the over-protective default.

### The wiring gap you should know about

`pre_trade_check`, `circuit_breaker`, portfolio-heat and drawdown breakers were part of the removed
scalp-era stack. **Nothing in `vivek_run.py` or `vivek_bot.py` calls any of them.** The bot book is
guarded by the daily/weekly loss guards and the position/notional/sector caps — *not* by portfolio
heat, a drawdown breaker or a consecutive-loss breaker. Wiring those up would change which trades
get taken, so it is an open owner decision, not a refactor.

## Part 7 — The data layer

### Source

**`yfinance`, pinned.** Free, ~15 minutes delayed, and **survivor-biased** (today's universe, so
delisted names are missing from history — every backtest inherits this). Moving to a
production-grade provider (EODHD / Norgate) is an open owner decision.

### Universes (`scanner/universe.py`)

- **ASX:** full listing, ~2,000–2,212 names. Carries **GICS sectors for every row.**
- **NASDAQ:** Global Select, ~1,430 names. **Ships no sector column** — this is why the
  3-per-sector cap historically never bound on NASDAQ.
- **Crypto:** top **200** by market cap (`CRYPTO_UNIVERSE_SIZE = 200`), stablecoins filtered out,
  `per_page` carries ~30% headroom. **Honest expectation:** at 100 only 69 of 101 had Yahoo data,
  and a $100M liquidity floor cuts more — expect **~110–130 actually scanned**, not 200.
- `data_universe/` holds bundled CSV fallbacks.

### Sector data is a SIGNAL PATH

`data/sector_map.json` is **not display-only** — `vivek_run.run_market` merges it into the rows
`decide()` sees, so it changes which trades get taken. Back-fill has three sources in order:
today's scan rows → the market's universe file → the cache. **Enrichment only ever writes into a
blank field** — a sector shipped with the universe wins, and an empty cache is a no-op, never a
clear. **Treat sector-cache edits as trade changes.**

### Frame caching and staleness

- `merge_with_cache` back-fills tickers Yahoo dropped this run from the last-good cache.
- **`FRAME_CACHE_MAX_AGE_DAYS = 10`** is the ceiling. Without it, a ticker Yahoo hadn't returned
  since March was handed to the scanner as today's bars — *a fossil price can fabricate a stop-out
  as easily as hide one.* Refusing a frame can only ever remove a name, never add one.
- `save_frame_cache` **refuses to write an empty dict**, so a totally-failed Yahoo run leaves the
  old cache on disk rather than wiping it.
- Frame age is measured in the **market's own calendar**, not the runner's local date. The tz
  fallback fails closed.
- **Age travels with the price:** `scan.py` publishes a sparse `price_age` → carried in
  `<market>_prices.json` → `journal.js` badges stale marks (`.jr-stale`). **Sparse, and the
  `delete` is load-bearing** — absent means fresh, and a name returning to the scan must actively
  *lose* its key, or the badge never clears and you learn to read past it.

### Error reporting

`scanner/scanerrors.py` is the shared reporter. Every per-ticker exception is surfaced (a name that
throws every session must be distinguishable from one that never sets up), and a market that fails
*entirely* is tracked by `run.py` rather than printing one line and exiting 0.

| `phasemap/<market>/latest.json` | `phasemap/run.py` | phasemap page, confluence |
| `phasemap/<market>/narrations.json` | `phasemap/run.py` | phasemap page (sidecar) |

| `vivek_backtest*.json` | backtest workflows | system page, Insights |
| `book_stress.json`, `edge_summary.json` | edge pipeline | journal tide line, edge card |
| `fx.json`, `market_caps.json`, `sector_map.json`, `sectors.json`, `events.json` | various | various |

### Publishing rules (hard)

1. **All writes go through `output.write_json`** — atomic (temp + `os.replace`), NaN-safe, explicit
   newline. `allow_nan=True` once meant a single NaN emitted a bare `NaN` token and the browser's
   `response.json()` rejected the **entire market file** — a blank page for one bad bar.
2. **`newline="\n"`** so a local Windows run can't rewrite every artefact with CRLF.
3. **A new published file is a new payload cost.** The dashboard already ships ~4.5MB of data. See
   Part 13 on the Lighthouse budget.

### Front-end conventions (hard rules)

1. **iOS-style dark theme.** Tokens live in `styles.css :root`.
2. **One timestamp convention: Melbourne on screen**, market-local/UTC in tooltips (`PM.fmtMelb`).
3. **Every edit to any `public/js/*.js` or `public/css/*.css` must bump its `?v=` in every
   referencing HTML page.** Assets are cache-first in the service worker; skip the bump and a
   returning visitor never gets your change. Read the current numbers from the HTML, never from docs.
4. **Then re-stamp `public/version.json`.** Its version is `YYYY.MM.DD-<8 hex>` where the hex is a
   digest of every versioned asset reference across `public/*.html` **plus** `sw.js`'s `CACHE` name.
   `tests/test_version_stamp.py` fails until it matches and prints the exact value to write. This is
   the *only* new-deploy signal an open tab has.
5. **PWA:** `sw.js` — network-first for `data/` and HTML, cache-first for `?v=` assets, never caches
   `/api/`. Bump its `CACHE` name on breaking changes.
6. **Escaping:** all interpolated values go through `esc()`. `test/escaping.test.js` (203
   assertions) enforces the contract across every shipped JS file.

### The Eyes worklist (a good example of the design philosophy)

WHAT NEEDS MY EYES is a *worklist you walk*, not a dashboard. Its dismissal rule went through four
iterations because each earlier one was a treadmill:

- v1 keyed to the scan's `generated_at` → every hourly re-scan wiped it.
- v2 keyed to the Melbourne day → midnight brought everything back.
- v3 a 7-day window → a weekly setup re-appeared on day 8 having done nothing.
- **v4 (current): a dismissal lasts until the name's ALIGNMENT MATERIALLY CHANGES.** Each mark
  stores a fingerprint (`lenses + direction + VIVEK grade`); the name returns only when today's
  fingerprint differs. Same setup for three weeks = you see it once. A dual becoming a triple, a
  direction flip, or an upgrade to A+ **is** new information and comes back.
- `"*"` is the UNKNOWN fingerprint — the chart marks a name on arrival without knowing why it was
  aligned, and it matches any state so nothing reviewed reappears; the deck upgrades it to the real
  fingerprint on the next render.
- **Products (LICs/ETFs/preferreds) are dropped entirely, not marked** — a marker the eye has to
  skip is still something you read.

### THE SCHEDULING PATTERN — read this before adding any cron

**Crons fire a deliberate SUPERSET; an in-job gate decides.** Melbourne and New York change daylight
saving on *different dates*, so the UTC hour of either session slides by an hour twice a year and by
**two** relative to each other. Every attempt to write market hours as fixed UTC has been wrong for
part of the year (one version would have left the ASX open unscanned for four weeks every October).

`scan.yml`'s gate asks the tz database, in the **market's own calendar**:

```python
MARKET_SCAN_WINDOWS = {
    "asx":    ("Australia/Sydney",  11*60,      16*60+45),   # open+1h .. close+auction
    "nasdaq": ("America/New_York",  10*60+30,   16*60+45),
}
```

Result: **7 ASX scans 11:07→16:30 local and 7 NASDAQ 10:37→16:07 local, identically in all four DST
regimes**, and **nothing outside a session**. The 16:45 tails are load-bearing — the ASX closing
auction prints ~16:10–16:12 and the Discord digest refuses to send without a scan stamped after it.

**Crypto is not in scan.yml.** `crypto_bot.yml` owns it outright, hourly, seven days.

> **Lesson learned the hard way (2026-09-20):** the old weekend cron was *commented* "crypto only"
> but passed **no market**, so scheduled runs fell through to `all` and re-scanned ~2,000 ASX names
> four times a day on a shut market — eleven full weekend scans in one weekend. **A comment is not
> a gate.**

### The `scan` mutex

`scan.yml`, `crypto_bot.yml` and `close_position.yml` share `concurrency: group: scan` so two writers
can never touch the paper book at once (load-bearing: the 30-position cap is global, so concurrent
writers could each read "23 open" and both open).

**That group sits on the JOBS, not at workflow level.** GitHub keeps only one pending run per group
and cancels the previously-pending one, so workflow-level scoping put cheap gate jobs in the same
queue and every freshness backstop was being evicted. `tests/test_workflow_mutex.py` fails if you
move it back up. **If your new lens is read-only, do NOT join this group.**

### Silent-failure protection

Callers of `scripts/assert_staged.sh`: scan, crypto_bot, phasemap, backup_book, reco_note, and
close_position (gated to `journal_type=bot`). Every caller runs it **after staging** — a scheduled
run that stages none of its must-change outputs **fails loudly** instead of finishing green. (A real
staging bug once ran green five times while committing nothing.)

`assert_staged.sh` is **ANY-OF**: it passes if at least one listed path has a staged diff. Never list
a derived view alongside the canonical file, or a run that regenerated the view passes while the
real write was lost.

**`git add a b` is banned repo-wide.** With `b` missing it exits 128 and stages **neither**. Stage
one path at a time. `tests/test_workflow_hardening.py` bans the *shape* by counting pathspecs.

### The watchdog

`scanner/watchdog.py`, hosted in `kill_switch.yml` and `crypto_bot.yml`, probes content timestamps
and GitHub run history, alerting on staleness with strict noise rules: **say it once, remind every
`WATCHDOG_RENOTIFY_HOURS`, and announce recovery** (the thing a red run structurally cannot do).

`WATCHDOG_RUNS` maps workflow → max age. **`scan.yml`'s entry is `session_aware`** — it measures only
hours a market was actually *open* (zero across a weekend, ~11 a weekday), because Friday's last scan
to Monday's first is ~52 wall hours and a naive threshold would cry wolf every weekend.

**When you add a workflow that commits data: give it an `assert_staged` call and a `WATCHDOG_RUNS`
entry.**

## Part 12 — Alerting and the Discord digest

### History: the alert router is gone

The old `alert_dispatch` Discord router was **removed entirely on 2026-08-27** on the owner's
ruling. Two stacked failures had kept it silently dead for months and are worth remembering:

1. The stored webhook URL began with **U+FEFF** (an invisible BOM). `urllib` rejected it as
   `unknown url type`. A `.strip()` never removes U+FEFF — it is category Cf, not whitespace. Fix:
   `config.clean_secret()` trims BOM/zero-width characters at every credential boundary.
2. **Discord's edge 403s Python's default User-Agent** as a bot. A named UA fixed it.

Telegram and SMTP remain unconfigured. **So the only alarms today are GitHub's own red-run emails
and `::warning::` annotations on run pages.** Any routable event logs "NOBODY WAS TOLD".

### Live: the morning plays digest

`scripts/morning_plays.py` + `morning_plays.yml`, using its **own** secret
`DISCORD_MORNING_WEBHOOK_URL` (deliberately a different name from the removed one).

**Delivery times:**

| Slot | Lands | After DST (~5 Oct) |
|---|---|---|
| **ASX** | **~16:50 Melbourne**, Mon–Fri | ~16:50 |
| **NASDAQ + Crypto** | **~07:50 Melbourne**, Tue–Sat | ~08:50 |

**Two gates must both pass:**
1. **Wall-clock floor** — Melbourne at/past 16:30 (ASX) or 06:30 (US).
2. **Post-close data gate** — the scan it reads must be stamped at/after that market's most recent
   weekday close (`MORNING_PLAYS_SLOT_GATE`: ASX **16:12 Sydney**, NASDAQ **16:05 New York**). The
   NASDAQ time is 16:05 and *not later* because under EST the 21:07 UTC scan is 16:07 NY and is the
   only post-close scan of the day — a 16:15 gate would silence the US digest all winter.

Before the gate passes the run is a **silent no-op that marks nothing**, so the next attempt retries.

**Delay-proofing:** GitHub's free cron has run these 2–5 hours late and once not at all. Each cron
maps to a slot *name* and the slot sends when Melbourne is **at or past** target **and** a per-day
marker says it hasn't gone out today. So a late cron still delivers, and the second DST cron can't
double-send.

**7-day de-dup:** a ticker sent within `MORNING_PLAYS_DEDUP_DAYS` (7) is skipped, because the owner
charts each name and shares it on, and a weekly setup persists for days. Only **actually-delivered**
tickers are recorded — a failed post records nothing and marks no slot done. State lives in an
`actions/cache` file, so the job stays **read-only to the repo**.

**Message format (updated 2026-09-21 at the owner's request):** grouped by market, then by
(conviction label × cell count), with the **🎯 marks on the group header** and the tickers **clean,
one per line** — so a drag-copy is pure symbols he can paste to a friend.

```
**ASX PLAYS**
High conviction A+ 🎯
GYG
PMT
XRF

High conviction A+ 🎯🎯
ENR
```

Filter: **LONG only, never shorts; never a fund/REIT/LIC/preferred.** No entry/stop/RR clutter.

## Part 13 — Testing and CI gates (where a careless new lens gets blocked)

`test.yml` runs three jobs on **every push**: `python`, `javascript`, `e2e`.

### `python` job
`pytest -q` over `tests/` (~72 files) and `phasemap/tests/`. **New `tests/*.py` files need no
registration** — pytest collects the directory.

### `javascript` job
**22 suites, each with its own `node test/<file>` step** (27 node invocations in the workflow).

> **THIS IS A GATE, NOT A CONVENTION.**
> `tests/test_screenshot_determinism.py::test_every_javascript_suite_has_a_step_in_the_workflow`
> walks `test/*.test.js` and **fails the push** if any suite has no step. An unregistered suite is
> not a weak gate — it is a file full of green assertions CI never runs.

**House pattern for JS tests:** they **slice the shipped source file** and execute the real
declarations, rather than re-typing a fixture. A re-typed fixture drifts in step with the bug it is
supposed to catch. Sandboxes are built with `new Function(body)()`, **not** `vm.runInContext` — a
`vm` context is a separate realm, so its `Array.prototype` differs and every cross-realm
`deepStrictEqual` fails for reasons unrelated to the code under test.

### `e2e` job (Playwright, five steps, in order)

1. **smoke** — loads index/recs/specs/phasemap/journal, asserts rows render, filters narrow, sorting
   works, no horizontal overflow at 320/360/390/430px, and **zero uncaught page errors**.
2. **hang-probe** — a hung fetch must become a timeout and a "Tap to retry".
3. **mobile screenshot matrix**.
4. **Lighthouse budget** — CLS + a transfer tripwire.
5. **screenshot-diff** — desktop + 390px, <2% drift.

> **A failing step ABORTS the job.** A green step later tells you nothing if an earlier one is red.

**The e2e job is fully reproducible locally** — this is the single most useful debugging fact in the
repo:

```bash
export PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers   # preinstalled; NEVER `playwright install`
node test/e2e/smoke.e2e.js
node test/e2e/screenshot-diff.e2e.js               # needs pixelmatch + pngjs
```

### Two gates that were once measuring the wrong thing

Both are worth understanding because they are the traps a new lens will spring:

- **The screenshot gate was failing on the CALENDAR.** `journal.js` renders relative ages, so a
  cached baseline two days old drifted 2.39% against a 2% budget. Fixed three ways: the page clock
  is **frozen** to the fixture book's own `updated_at` via `ctx.addInitScript`; the cache key
  **digests the fixtures** (`hashFiles('test/e2e/fixtures/data/*.json')`); and a `.clock` sentinel
  inside the baseline directory **discards and re-cuts rather than failing** when the baseline was
  drawn by a different clock. There is deliberately **no `restore-keys`** on that cache — a prefix
  fallback would restore the very baseline a bump exists to discard.
- **The Lighthouse budget was measuring the TAPE.** It gated on how many ASX stocks happened to set
  up that day (4.15MB of committed scan data). Fixed by serving a **staged root** — symlinks to
  every `public/` entry except `data`, plus one pointing `data` at the e2e fixtures — so both e2e
  gates measure the same deterministic page. The **real** payload is still measured, printed every
  run, warns past 7MB, and **gates never**.

**Consequence for you:** `test.yml`'s path filter **deliberately excludes `public/data/**`**, so the
~20 daily scan commits never trigger CI. Any gate that reads `public/data/` becomes a delayed-action
fuse pointed at whoever pushes code next.

### Intentional visual changes

If your change legitimately alters a photographed page, **bump the screenshot baseline cache key** in
`test.yml` (`screenshot-baselines-vNN`). It is currently at **v22**. A test asserts it stays ≥ v11
and that no `restore-keys` appears.

## Part 14 — The hard project rules

These are enforced by tests and by convention. Breaking them is how CI goes red.

1. **Git first, always.** CI and other sessions push constantly. Before any commit:
   `git fetch -q origin main && git rebase -q origin/main`. Push to **`main`** — Cloudflare Pages
   deploys `main`; feature branches do not deploy.
2. **Version bump:** every `public/js|css` edit bumps its `?v=` in every referencing HTML page,
   then re-stamp `public/version.json`.
3. **Config first:** every new threshold or constant goes in `scanner/config.py` (or
   `phasemap/config.py`) **before use**. Bot rule constants are published to `bot_rules.json` each
   scan — never hardcode a number the dashboard also reads.
4. **PhaseMap spec is law.** Never change detection maths or zone definitions without asking the
   owner. Bump `RULESET_VERSION` on any parameter change.
5. **Tests gate everything.** `python -m pytest -q` plus `node test/*.test.js` must be green.
6. **Pinned deps.** `requirements.txt` pins trade-path packages exactly. Bump deliberately; never
   loosen to `>=`.
7. **Atomic writes** for any journal/state JSON (temp + `os.replace`).
8. **ASCII-only prints in scanner code** — Windows consoles are cp1252 and choke on arrows and
   em-dashes.
9. **CF Functions are Workers runtime** — no Node builtins.
10. **One YAML trap, learned 2026-09-21:** an `env:` key with nothing under it makes GitHub unable
    to build the workflow — it produces a **zero-job `startup_failure`** and emails it as a failure.
    `bash -n` cannot catch this (it checks shell inside scalars, not YAML structure). **Validate
    workflows by loading them with a YAML parser and asserting every step `env` is a mapping.**

## Part 17 — THE NEW-LENS PLAYBOOK

You want to add a **fourth scanner**, under a new name, **without breaking anything**. Here is
exactly how, derived from how TURTLE was added *and cleanly removed*.

### 17.0 The single governing principle

> **Build it so it could be deleted tomorrow in one commit.**

Every design decision below follows from that. A lens that is *removable* is also a lens that is
*non-breaking*, because removability and isolation are the same property. TURTLE proved this: a
whole lens came out in one commit and **nothing in `broker/`, the bot book or the confluence
machinery changed**, because its fences were test-pinned from day one.

### 17.1 Decide three things first (before any code)

1. **Is it REPORT-ONLY or does it feed trades?** Default and strong recommendation: **report-only**.
   A report-only lens can ship autonomously. Anything that changes which trades get taken needs the
   owner's explicit sign-off with numbers. HORIZON and REGIME were report-only by construction and
   said so in their module docstrings.
2. **Does it join the confluence machinery?** Confluence currently means "2+ of the three lenses
   agree on direction". Adding a fourth voice **changes what every existing confluence surface
   shows** — the ⨂ pill counts, the Eyes strip, the ALERTS log, and the edge pipeline that ingests
   `alert_history.json`. **Default: NO.** Keep it out of confluence for v1 and make that an explicit
   later decision.
3. **What is it called?** Pick a single lowercase token used everywhere:
   `scanner/<lens>.py`, `<LENS>_*` config prefix, `public/<lens>.html`, `public/data/<market>_<lens>.json`,
   `.github/workflows/<lens>.yml`, `tests/test_<lens>.py`, `test/<lens>.test.js`.
   Avoid a name that collides with an existing field or state string.

### 17.2 The file manifest

```
NEW FILES (all additive):
  scanner/<lens>.py              the engine — pure functions, deterministic, no I/O
  scanner/<lens>_run.py          the CLI: python -m scanner.<lens>_run --market asx
  scanner/config.py              ADD a <LENS>_* block (edit, don't create)
  .github/workflows/<lens>.yml   its own schedule, its own concurrency group
  public/<lens>.html             its page
  public/js/<lens>.js            its front end
  public/css/<lens>.css          its styles
  public/js/nav.js               ADD the nav tab (edit)
  tests/test_<lens>.py           pytest — auto-collected, no registration
  tests/test_<lens>_fences.py    THE FENCES (see 17.4)
  test/<lens>.test.js            JS suite — MUST get a step in test.yml
  .github/workflows/test.yml     ADD the node step + path filter entries (edit)
  public/data/<market>_<lens>.json   published output (written by CI, not committed by you)
```

### 17.3 Engine shape — copy the existing contract

Make your engine look like the others so every downstream habit works:

```python
# scanner/<lens>.py
def evaluate(frame, *, market: str, cfg=config) -> dict | None:
    """Pure. Takes a bars DataFrame, returns a result row or None.
    Deterministic: same bars in, same dict out. No network, no file I/O, no clock."""
```

```python
# scanner/<lens>_run.py
def run_market(market: str) -> dict:
    frames = data.download_market(market)          # reuse the shared downloader
    rows = [r for r in (evaluate(f, market=market) for f in frames) if r]
    output.write_json(DATA / f"{market}_<lens>.json", {
        "generated_at": dt.datetime.now(dt.timezone.utc).isoformat(timespec="seconds"),
        "market": market,
        "ruleset_version": config.<LENS>_RULESET_VERSION,
        "results": rows,
    }, newline=True)
```

**Non-negotiables:**
- **Reuse `scanner/data.py`** for downloads — you inherit the frame cache, the 10-day fossil
  ceiling, market-calendar age measurement and the error reporter for free. Do **not** write a
  second yfinance path.
- **Publish through `output.write_json`** — atomic and NaN-safe. A bare `NaN` token kills the whole
  file in the browser.
- **Include `generated_at` and a `ruleset_version`.** The former is how every freshness surface
  works; the latter is how you version parameter changes without ambiguity.
- **ASCII-only prints.**
- **Every threshold in `config.py` under a `<LENS>_` prefix**, with a comment giving the rationale
  and the measured near-miss.

### 17.4 THE FENCES — write these tests on day one

This is the part that makes the lens non-breaking. Add `tests/test_<lens>_fences.py`:

```python
BROKER = ROOT / "scanner" / "broker"

def test_nothing_in_broker_imports_or_mentions_the_new_lens():
    """The lens must not be able to change which trades get taken."""
    for p in BROKER.rglob("*.py"):
        src = p.read_text(encoding="utf-8")
        assert "<lens>" not in src.lower(), f"{p.name} references the new lens"

def test_the_lens_never_writes_an_existing_published_artefact():

def test_the_lens_does_not_touch_the_confluence_machinery():

def test_the_engine_is_deterministic_and_offline():

def test_every_threshold_lives_in_config():

```

Mirror the `is_product` precedent: **fence in both directions** — assert the lens can't reach the
bot, *and* assert the bot doesn't reach the lens.

### 17.5 The workflow

```yaml
name: <Lens> scan
on:
  schedule:
    # SUPERSET crons + an in-job gate. See Part 11. Do NOT write fixed UTC
    # market hours — they are wrong for part of every year.
    - cron: "17 0-6 * * 1-5"
  workflow_dispatch:
permissions:
  contents: write
concurrency:
  group: <lens>          # its OWN group. Do NOT join `scan` unless it writes the book.
  cancel-in-progress: false
jobs:
  scan:
    runs-on: ubuntu-latest
    timeout-minutes: 30          # every job here is bounded
```

Checklist:
- [ ] **Own concurrency group.** Joining `scan` puts you in a queue where GitHub cancels the
      previously-pending run — you would start evicting the freshness backstops.
- [ ] **A timeout.** One stuck run silently costs a session.
- [ ] **`assert_staged.sh`** after staging, listing the canonical output paths (ANY-OF semantics).
- [ ] **Stage one pathspec at a time.**
- [ ] **A `WATCHDOG_RUNS` entry** in `config.py` if it commits data. Consider `session_aware` if it
      only runs in market hours.
- [ ] **Validate the YAML with a parser** before pushing (Part 14, rule 10).
- [ ] If it must not scan a shut market, **gate in-job on the tz database** using
      `MARKET_SCAN_WINDOWS`, not on cron arithmetic.

### 17.6 The front end

- [ ] `public/<lens>.html` + `public/js/<lens>.js` + `public/css/<lens>.css`.
- [ ] **Hide the surface silently when its JSON is absent.** Every existing panel does this, so a
      market that has never run degrades to nothing rather than to an error. Scope the `.catch()` to
      **the fetch and parse only** — put the renderer *after* it, or a renderer bug becomes
      indistinguishable from "the data isn't there yet" and the panel silently vanishes for weeks.
- [ ] Route every interpolated value through `PM.esc()`.
- [ ] Use `PM.fetchTimeout` so a hung connection becomes a rejection (the hang-probe e2e step will
      check this behaviour if your page is added to it).
- [ ] Add the nav tab in `nav.js`.
- [ ] **Bump `?v=` for every new/edited asset in every referencing page, then re-stamp
      `version.json`.**
- [ ] Consider bumping `sw.js`'s `CACHE` name if you change the shell.

### 17.7 The tests and the CI gates

- [ ] `tests/test_<lens>.py` — engine behaviour. Auto-collected.
- [ ] `tests/test_<lens>_fences.py` — the fences above.
- [ ] `test/<lens>.test.js` — **and its `node test/<lens>.test.js` step in `test.yml`, or the push
      fails.** Slice the shipped JS rather than re-typing a fixture.
- [ ] **Path filter:** add `public/<lens>.html`, `public/js/<lens>.js`, `public/css/<lens>.css` and
      `scanner/<lens>*.py` to `test.yml`'s filter if not already covered, or the suites that read
      them won't run when you edit them.
- [ ] **e2e:** if you add the page to `smoke.e2e.js` (recommended — the 320px overflow check is
      cheap insurance), also add it to the screenshot matrix, and **bump the screenshot baseline
      cache key** because you have changed a photographed page set.
- [ ] **Run the full gate locally before pushing:** `pytest -q`, every `node test/*.test.js`, and
      `node test/e2e/smoke.e2e.js`. This is the step that was skipped in one recent session and it
      cost several red-run emails.

### 17.8 Payload budget

A fourth lens publishing three market files adds to a dashboard payload already around 4.5MB. The
Lighthouse gate is fixture-pinned so it **will not fail you**, but it prints the real payload every
run and warns past 7MB. Keep your published file **slim** — follow PhaseMap's precedent: a slim
`latest.json` with narrations in a sidecar, loaded lazily. If your page needs 500KB of detail,
publish it as a separate file the page fetches **on demand**, not on load.

## Part 19 — Glossary

| Term | Meaning |
|---|---|
| **Lens** | One independent scanner/strategy (VIVEK, PhaseMap, Specs) |
| **R** | Reward measured in units of the trade's own initial risk. The only comparable series across sizing changes |
| **PF** | Profit factor — gross wins ÷ gross losses |
| **Cell** | A (timeframe × entry type) bucket, e.g. "1W reclaim". The unit of the conviction rule |
| **Armed** | A plan's entry trigger condition is live right now |
| **`level_tf`** | Which timeframe's 200-SMA the headline level belongs to (`weekly`/`3d`/`daily`) |
| **`grade` vs `grade_raw`** | Hysteresis-smoothed (shown in UI) vs unsmoothed (what the bot buys) |
| **The book** | `journal/vivek_bot_book.*.json` — the paper track record, the only one |
| **Confluence** | Direction-aligned active setups on 2+ lenses |
| **The deck** | `index.html`, the main scanner view |
| **`is_product`** | Server-side verdict that a row is a fund/REIT/LIC/preferred, not an operating company |
| **assert_staged** | CI guard: a run that stages none of its must-change outputs fails loudly |
| **The mutex** | `concurrency: group: scan` — serialises every writer of the paper book |
| **w3 / hc4-1** | Pre-registered live cycle tags stamped on book rows for cohort analysis |
